# Agent 原生评估器交付实施与验收计划

> 执行者采用`superpowers:executing-plans`逐包实施，代码使用测试先行；需要独立并行子任务时才分派。技能默认的自动建worktree、提交或发布与项目权限冲突时，服从项目边界。

**目标：**交付在当前Codex新会话中可从附件走到可追溯报告的单一插件包，内嵌标准Skill；不要求独立Skill包、其他Agent或跨操作系统验收。  
**架构：**Skill组织工作流，宿主适配记录实际执行，产品服务协调任务，复用现有Store/Journal/六维内核。专业效果随后由同事/业务方确认，不要求开发者编写专业黄金答案。  
**技术栈：**标准Skill Markdown、现有插件封装、本地Python≥3.12、SQLite、内容寻址原件、pytest；不增加在线依赖。  
**Spec：**[AG1-SPEC 1.1-candidate](D:/UGit/kth-irl-hybrid/docs/specs/agent-evaluator-delivery-v1.md)。本计划与Spec必须共同阅读。  
**执行状态与权限：**只读[CURRENT](D:/UGit/kth-irl-hybrid/docs/CURRENT.md)，本计划不复制日常进度。文档分类见[文档导航](D:/UGit/kth-irl-hybrid/docs/README.md)。

Owner采用本Spec并批准离线工程后，M1–M6可以连续执行；每包记录检查点，集中送G1。真实宿主模型/研究调用须G2新许可，不能从“工程开工”推定获准。G3交付后才集中进行G4专业反馈。

### 规划就绪与可编码的区别

本计划已经提供全产品路线与验收框架，但接口方向和示例断言不是完整、可直接执行的实现规格。每包进入编码前，由执行者在本包小节补齐以下技术合同，作为该包首项工作连续完成，不要求Owner逐字段批准：

1. 实际函数签名、输入/输出字段、版本与最大范围。
2. 所读写的Store/Journal对象、可信输入来源、事务/并发/幂等及中断恢复边界。
3. 调用者、全部消费者、旧读新写适配与错误/阻断状态。
4. 覆盖本包AT场景的具体测试输入、预期断言、实际测试文件和命令。
5. 精确修改allowlist与自有新编/引用/机械提取来源。

完成后将合同版本登记在CURRENT和阶段交接，再先写失败测试；不能根据示例字段自行跳过安全闭包。细化改变业务语义、方法、权限或验收时才升级为Spec变更。

### 3.1 M1：Agent入口与执行桥

**接口方向：**拟新增`ProductSession(case_dir)`作为产品协调器，使用既有Store/Journal；不是新存储系统。拟新增`prepare_submission(request)`、`pending_tasks(run_id)`、`submit_host_result(task_id, envelope)`、`advance(run_id)`、`status(run_id)`。它们由实际内部CLI工具暴露，用户不调用这些接口。

`prepare_submission`接收显式附件、用户问题及宿主能力，不提前生成专业结果；`pending_tasks`只返回该run合法任务；宿主返回必须绑定任务/输入/角色/上下文/输出；`advance`不隐式联网。字段和错误码在编码前于本节一次冻结。

- [ ] 先写入口测试：缺宿主能力时返回具体阻断；用户未确认范围时专业任务为空；模拟/人工/API/宿主来源不能互换；其他任务的结果被拒。
- [ ] 运行新测试确认功能缺失或断言失败，保存原退出码；不以导入异常作为最终RED证据。
- [ ] 增加宿主执行桥和Skill最短主流程，支持一次受控任务导出、封存、消费和状态恢复。
- [ ] 在同一产品服务上完成离线往返，由独立审核者检查插件内Skill行为；不安装到用户全局目录，不改marketplace。
- [ ] 记录实际接口、源码hash、测试证据和剩余未接阶段，进入M2。


这里的`host_agent`是拟新增来源标签，不是现有接口已经接受的字段。没有真实宿主记录的测试必须另标`simulated`，上述实际宿主分支由适配测试输入验证，不冒充真实调用。

- [ ] 输出版本、包hash、设计说明、测试/限制、具名比较与协作反馈格式；独立工程审核后进入G2。

示例验收断言：

```python
assert resumed["result_digest"] == before_crash["result_digest"]
assert additional_dispatches == 0
assert bundle["implementation_ref"] == review_receipt["implementation_ref"]
assert bundle["professional_acceptance"] == "not_evaluated"
```

### 3.7 M7：真实Agent验收与交付

此包不以开发机直接调用CLI代替Agent执行，也不把离线替身标为真实。G2前整理材料、宿主、实际工具、模型/API、窗口、预算、失败处置及现有历史消耗建议，一次交Owner批准。

- [ ] 在当前Codex的全新会话加载实际插件包，只给显式附件和自然语言任务，不能继承开发对话答案。
- [ ] 完整真实业务链通过插件内标准Skill执行；记录实际Codex版本、可用工具、角色上下文与包hash，不以终端直接运行结果替代。不做独立Skill包或其他宿主的第二轮验收。
- [ ] 第一主Case采用微玖BP+四访谈；正常发现/确认范围，不限定只看页17或强设某等级。需要改时点先明确，不改旧Case。
- [ ] Monako作为另一输入结构与去重/单元边界样本；完整运行须在授权范围内。未获其运行许可时保留AT-15相应缺项，不能宣布全部验收。
- [ ] 实际执行研究和专业角色链，保存请求/返回/原文/用量/失败；系统不能用“人工导入结果”替代主自动路径。
- [ ] 换一个新的Codex会话从工件恢复，查看结果和关键trace；不重做已封存动作。
- [ ] 形成工程交付结论与协作包，专业状态为待同事/业务方复核；不自动发送给任何人。

真实业务结果不足可以是诚实结果，但必须已经完成应执行的链路。若全部停在资格前、没有实际研究/专业返回，则是工程闭环未验证，不是交付完成。

## 4. 验收矩阵

| AT-12 | 详细/简明/审计视图同一结果身份；正文不新增事实、删反方或改权限 | M5，E＋H |

### 验收失败的处理

- 工程缺陷：同合同内连续修复，补受影响测试后集中复验。
- 同类阻断经两次集中修复/复验仍存在：停在受影响模块，提出替换/缩范围的具体决定，不继续无限叠补丁。
- 原件、方法、权限或未知外部结果问题：停止受影响执行，不以通过演示为由降低门。
- 专业争议：不作为开发者失职，也不自动改规则；交同事/业务方，记录证据和版本。
- 没有真实授权：可以达到`offline_candidate_ready`，不能写`engineering_delivered`。
- 缺真实正向专业样本：明示专业正向质量未验，不用合成支持补成真实通过。

## 5. 测试与证据操作

实施者获准后生成实际StageRoot，并设置`KTH_CASE_ROOT`为该目录。使用现有项目解释器，不安装依赖。测试产物使用全新目录、禁缓存/字节码，保留原conftest网络与凭据保护。

新增测试文件实际创建后，在`D:\UGit\kth-irl-hybrid\plugin`运行。下例是M1的预定命令，不宣称文件现在已存在：

```powershell
$env:PYTHONDONTWRITEBYTECODE = '1'
$env:PYTHONUTF8 = '1'
$env:KTH_CASE_ROOT = $StageRoot
$testRoot = Join-Path $StageRoot ('tests\m1-' + [guid]::NewGuid().ToString('N'))
```

后续各包按文件表运行精确新增集及实际受影响既有测试；保存真实命令、退出码和日志，不只写通过数量。Store/Journal共享修改需扩大相关回归，但不打开历史Case库或无因重跑全部旧评估。

每个StageRoot仅维护一份`阶段交接.md`，链接`evidence/`、`tests/`、`cases/`、`reports/`和`packages/`实际工件。不预建空工件或伪造调用日志。

## 6. 跨对话检查点与防偏航

每次结束或上下文切换前，主执行者在CURRENT更新：

```yaml
spec_id: AG1-SPEC
spec_version: 1.1-candidate
implementation_ref: 实际HEAD加工作树清单摘要
current_package: M0至M7中的实际位置
package_state: not_started | implementing | candidate_ready | accepted | blocked
authorization: 本轮实际允许范围和禁止事项
stage_root: 实际路径或尚未创建
requirements_covered: 实际AR编号
acceptance_evidence: 实际AT编号和证据链接
open_issues: 阻断与非阻断分列
next_action: 一个明确的下一动作
```

这些是维护字段说明，不是待用户填写的技术模板。执行者填实际值，不能写“全部完成”而缺证据。

新对话先核身份再继续CURRENT下一动作，不重新设计产品、不凭旧对话记忆猜状态。若CURRENT与工件冲突，先据证据校正并记录差异，不能覆盖已有结果。

每次准备修改代码前回答三问：服务哪个AR需求？由哪个AT场景证明？是否必要于当前包出口？无明确答案的改动进入待办，不进入当前交付范围。

业务/范围变更使用Spec变更记录，包含原因、影响需求/文件/验收、替代选项与Owner决定；工程细节修正留本包交接即可，不制造审批流水线。

## 7. 给同事及其Agent的交付内容

1. 本Spec、实现结构图及明确保留/替换理由。
2. 精确源码/包身份、依赖与宿主能力、实际安装/加载步骤。
3. 经许可的输入清单、时点、单元、模型/方法/政策配置及真实结果。
4. 原文—解释—准则—行动—报告的追溯入口和失败/恢复证据。
5. 旧新版差异，先区分输入/时点/单元/方法/政策变化，条件不齐不叫严格A/B。
6. 未验证专业项和反馈表：AR/AT、观察、依据、期望行为、影响与建议。
7. 同仓分支修改、受影响回归和审核规则；不自动推送/合并，不另建事实源。

工程交付后停止自动扩张，等待具名反馈。业务方不认可时定位到具体专业解释或需求，不以“代码全绿”驳回，也不靠再次全面重写回避。

#### C. M1-RD-002：一次性重建任务读取闭包

**保留：**现有`records.sqlite3`、v13表结构、Case UUID、`ag1.product-record.v1`类型边界、冻结输入/原件、Journal状态转换与attempt/fencing、不盲重发、v4宿主输入/返回合同及4MiB限制。**替换：**Store库存的浅比较、按run先过滤的调用顺序，以及`_task/_ticket/_sealed/status`各自拼出的重复状态规则。不是新增持久化“快照表”。

拟定接口及依赖方向：

1. `CaseStore.product_read_view()`提供只读SQLite事务上下文；其中`read_product_task_records() -> dict`读取实际行并解码，不能提前结束事务。`ProductSession._task_snapshot(run_id: str | None) -> dict`在此上下文内完成下述两阶段，返回本次调用内的`ag1.task-snapshot.v1`派生视图，不持久化、不跨调用缓存。相关Source/投影/coverage读取也使用同一Store连接；不混入另一Journal连接的时间点。Store不导入ProductSession。
2. **Case级身份和执行关系库存：先验证，再分组。**分母取Journal的`TASK::`任务、`task_attempts.task_key`及产品task/dispatch/response/consumption/scope_candidate中具名task引用的并集，保留真实对象键；不是只沿tasks查“对应”记录。每项重核task_id/body摘要/Journal.input_id、按保存的已支持合同版本由冻结request/inputs重算父run、Case/会话、票据/attempt/response包络与消费关系。孤儿attempt、派发、返回、消费或候选不得掉出分母；缺任一必需父记录受控拒绝。此阶段核身份、执行状态及内在引用，不将所有旧run用当前解析器重新作材料可消费性判定。
3. 身份/执行关系损坏使Case产品操作拒绝并具名故障；不能因记录自报“旧版本”跳过，也不能按可变run先筛选。产品task存在、Journal未登记、**无任何执行关系**的合法本地窗口记`registration_incomplete`，不伪装planned、不自动补账/派发/消费；明确窗口与孤儿执行关系不同。不检查无关旧任务命名空间，不承诺抵抗全部权威记录一起抹除或重造。
4. **目标run消费核验：**仅在已经完成Case库存校验后，对本次操作的目标run及其实际引用依赖重核冻结原件、Source/投影/coverage、材料白名单及角色输出引用；不能信任未重算的索引来选目标。创建新submission或revision只要求Case库存与父run身份合法，不消费父run材料；非DOCX run不因另一run的旧DOCX提取版本失效而阻断。旧run仍在库存中，失败/unknown和封存引用保持可定位。
5. 旧材料合同v1的DOCX若需要已退出的结构提取版本，目标run的消费/范围复用明确阻断为`legacy_extraction_contract`；这是识别到已支持的历史合同后的专用路径，不是捕获任意材料异常。`status`仍返回该run库存执行状态和具名阻断，不宣称材料/候选可用；实际身份损坏照常拒绝。显式新v2 revision可引用旧父run身份，保留旧材料/失败/unknown/候选，不读取或改写它们为新结果。新run不重派旧task，也不重置Case级历史动作/用量。
6. `_task/_ticket/_sealed/_candidate`改为同一视图的内部构件或薄访问器。`pending_tasks/status/advance/begin_task/submit_host_result/propose_scope/confirm_scope/scope`使用目标run消费核验；创建入口使用同一读取层的Case库存阶段。内部调用传递本次视图，不再嵌套创建不同快照。材料读取不反向调用任务快照，避免循环；同一目标run材料只核验一次。
7. **创建和公开材料读取分开：**`intake.project_product_materials(..., require_existing=True)`为拟增窄参数，默认值保留底层现有首次创建行为。所有公开`ProductSession.materials/discovery_batches`、内部CLI materials/batches及任务/范围读取必须传true；缺coverage根直接受控失败，不能补造。只有`prepare_submission`的显式准备路径可调用创建模式；对已存在run恢复未完成创建时，须先证明该run没有任何产品task、Journal产品任务/attempt、派发、返回、消费或范围引用，且冻结输入一致，才可复用已存在的未完成分片。已有任一任务关系时缺根属于完整性故障，连重新prepare也不能重建；正常已有根只读校验。保留无任务首次构建的中断/幂等，不把materials当隐式修复入口。
8. 写入口先核验完整相关集合再写，不能advance消费前几个任务后才发现后面损坏。消费发布在现有Store写事务中重核依赖并整批写入，失败零新增消费；用专用AG1批量发布方法，不在自开事务的旧`_put`循环外再嵌套事务。不跨事务缓存有效性，不在Store事务内调用另一连接的Journal写方法。begin/submit保留认领→落派发→外部边界、blob→response→Journal顺序及原fencing；读视图不冒充外部原子事务。

**关系/状态表是唯一推导规则，不用“没有返回=等待确认”：**

| 已核实的Journal与关联记录 | 任务视图与允许动作 |
|---|---|
| planned，无派发/返回/消费 | pending，可由获准begin认领；task_id分母保留 |
| claimed、external_actions=0，无返回，票据可尚未写或已写 | 本地派发前窗口，running/待受控恢复；不自动接管或重派；完整进程接管仍留M6 |
| dispatch_recorded，票据和attempt有效，无返回 | running；等待原返回，禁止第二次begin |
| outcome_unknown，票据有效，无返回 | unknown；无业务结果，不重派；只能接受同一票据确切迟到返回 |
| dispatch_recorded或outcome_unknown，有合法response | response_sealed或consumed；可验证消费；保留Journal原状态，不将unknown改写为succeeded |
| succeeded，response成功、Journal.output_ref匹配 | response_sealed或consumed；幂等读取/消费 |
| failed且external_actions=1，response为failed/cancelled | execution_failed，失败/取消保留原值，无业务输出；本合同先封存后记失败，因此response必需 |
| failed且external_actions=0，无response/消费 | 派发前本地失败，仍execution_failed；不能要求本不存在的外部返回，也不自动重试 |
| 上述终态缺必需response、错attempt/票据、消费无返回、非法组合 | `integrity:`受控工具失败；不发布业务状态、候选或新消费；CLI退出3 |

任务字段继续分列`journal_state/state/execution_status/source_mode`。汇总顺序明确为：完整性故障直接拒绝；任何失败/取消优先execution_failed（同时保留全部阻断原因）；其余能力/权限/旧提取版本阻断为blocked；然后未封存unknown优先于running，running优先于pending；只有没有未结束执行/消费阻断时才显示awaiting_scope_confirmation/awaiting_research。新增汇总枚举限定为`execution_unknown/execution_running/execution_pending`，更新Skill说明，不修改Journal枚举或业务求值语义。合法封存成功且Journal仍unknown同时展示；库存中“已封存”的观测不单独授予材料/角色输出可消费性，旧提取合同阻断不得被绕过。

#### D. M2-RD-001：统一DOCX内容块分类

**保留：**既有python-docx/OPC/XML能力、ZIP安全上限、默认`extract_docx_paragraphs(data)`的旧正文非空段落接口及tool、实际页眉/页脚枚举、Source/ImportRecord/原件与派生关系校验、coverage分片与只读恢复。**替换：**结构模式中story与cell的分叉扫描，以及“高层API取到的内容就是全部内容”的假设。不另造DOCX库。

1. 结构模式在`intake.py`内部使用一个`walk_docx_content(element, context, projection)`遍历器。context包含实际OPC member、story、嵌套单元路径和节点位置；同一规则用于body、实际header/footer、所有深度表格单元。使用现有解析器获取XML与文本，不安装依赖。
2. 每个被遍历内容节点只有三个出口：已支持并完整消费；明确非内容结构；具名unprocessed。只对**正向证明可忽略**的属性/空标记分类为非内容；未知节点默认unprocessed，不能靠“已知不支持标签列表”兜底。已支持容器仍枚举子节点，段落/run中的未知可见子树不能因`Paragraph.text`返回部分文字而漏记；不支持子树以最外未消费根记一次，不同时抽取其子文字冒充完整消费。未知子树两侧可读文字按连续文本跨度分别输出，复杂段定位增加`inline_span`及节点边界，不能无标识拼成连续引文；普通无缺口段落输出保持。
3. 按XML文档顺序进入段落、表格、实际单元和嵌套表格；不以`row.cells`的合并单元别名重复计算同一个XML节点，也不先聚合`cell.text`再把嵌套表格插到末尾。普通单段单元保留`table/row/column`定位；复杂单元按有序段块定位，增加`cell_paragraph`与`parent_cells`，同一文字不得重复进入发现。新定位/工具身份见兼容条款；不能降低旧“空段/空单元可定位”断言。
4. 正文member从实际document part取得；页眉/页脚与脚注/尾注/批注按实际关系、ContentType识别，不硬编码文件名。脚注/尾注/批注仍可整部件unprocessed，不要求全文解析。明确声明的内容部件若未进入可达解析集合，也须具名未处理，不能作为不存在。样式/主题/属性等明确非内容资源不当业务片段。
5. altChunk、内容控件、修订、文本框、字段、嵌入对象等不能完整消费的子树，在正文、页眉页脚、普通/嵌套单元任一位置均给`member + 节点路径 + 原因`；有关系时记录内部/外部或缺失关系，不访问目标、不渲染或执行。未知容器也适用；外部关系不触发网络。所有unprocessed继续进入既有coverage分母及partial/unprocessed终态。
6. 新结构提取tool使用`ag1-docx-structure.v3`，复杂单元定位变化使相关投影/片段/候选失效，不能回写旧结果。新提交材料合同使用`ag1.m2.v2`并参与run身份；读取既有v1时按其保存版本重算run身份，序列化兼容仍严格校验。旧DOCX快照若与新提取不符，明确要求显式新run；不维护旧解析器分支、不自动迁移、不借相同原件hash继承范围/Evidence。未受影响的v1非DOCX快照仍按原规则校验读取。新revision可引用旧父run的合法身份，不必消费其失效材料。
7. 创建与恢复继续复用现有覆盖构建规则，但完整性预期必须独立来自合成原始ZIP/XML清单。重建一致只能证明派生关系，不能自行证明“全部已看到”。遍历用显式栈避免Python递归深度成为隐含截断；沿用现有材料/ZIP安全上限，底层解析器的深度/安全拒绝必须给具名failed/未处理并保留输入分母，不降低输入上限来逃避测试。不增加后台索引、状态文件或进度脚本。

### 验收失败的处理

- 工程缺陷：同合同内连续修复，补受影响测试后集中复验。
- 同类阻断经两次集中修复/复验仍存在：停在受影响模块，提出替换/缩范围的具体决定，不继续无限叠补丁。
- 原件、方法、权限或未知外部结果问题：停止受影响执行，不以通过演示为由降低门。
- 专业争议：不作为开发者失职，也不自动改规则；交同事/业务方，记录证据和版本。
- 没有真实授权：可以达到`offline_candidate_ready`，不能写`engineering_delivered`。
- 缺真实正向专业样本：明示专业正向质量未验，不用合成支持补成真实通过。

## 6. 跨对话检查点与防偏航

本节是必须执行的工程纪律，不是另一个产品或工具项目。不新增进度脚本、hook、JSON状态文件或管理平台。主执行者负责落实，独立审核检查执行证据；不宣称文档能自动阻止一切违规。

### 6.1 单一状态与稳定身份

- Spec只定义产品需求与完成标准；本计划只定义工作项、接口和验收；CURRENT只记录实际进度和权限。README、AGENTS、恢复输入不复制实时状态。
- CURRENT记录检查点编号、采用的Spec/包内合同版本、核对时HEAD、相关未提交文件、当前包及工作项ID、实际权限、StageRoot、有效证据、未决问题和一个下一动作。未提交代码可继续保留，不能只用HEAD冒充受测身份。
- 已完成包在CURRENT保留一行汇总及具名证据入口；当前包列出各工作项状态。后续包写未开始，不能在切换工作包时丢掉未完成项。历史测试/裁决保留原身份，不作为另一份实时进度维护。
- CURRENT由一个主执行者维护。子任务只交付文件、版本、测试和遗留问题；主执行者核实后登记。不能直接把子Agent的“完成”回复当验收证明。

### 6.2 启动与恢复核对

1. 按恢复输入读现行文件，核对Owner最新权限、Spec版本及本包合同；不得从旧对话或过期窗口推定授权。
2. 实际查看分支、HEAD、暂存/未暂存差异和新增文件，与CURRENT检查点比较。只检查本仓和受影响范围，不全盘盘点、不读取凭据或保护Case。
3. 对本次准备依赖的“已完成”项，定位实际实现及具名原始测试/审核结果，核对实现身份、输入和验收层。路径存在、旧PASS或文档一句“通过”均不够；无关且未变化的历史不重审。
4. 有差异时先在CURRENT记录“上次声明、实际观察、影响范围、下一核实动作”。缺证或无法确定影响范围的项标为待复验；不能先沿用完成结论，也不能直接修改文档迎合代码而不核实。
5. 首次工作更新向用户简述实际位置、差异及本次工作项。只恢复已核实且获准的下一动作，不重新规划整个产品。

意外中断后，未登记代码保留为未验证工作。以最后一个证据完整的检查点为起点核实增量，不能把文件时间最新、任务执行过或对话摘要当成完成；不得自动重跑结果未知的外部动作。

### 6.3 状态与通过条件

| 状态 | 必须成立的事实 |
|---|---|
| 未开始 | 尚未开展，不隐去验收要求 |
| 进行中 | 已有实际工作，但实现/接线/验证尚未闭合 |
| 已实现，未验证 | 存在可定位实现；尚无对应版本的有效通过证据 |
| 自测通过，待审核 | 对应版本及受影响消费者的规定测试通过；保留实际命令、退出码和原始结果，不等于独立通过 |
| 已验收（注明层级） | 有对应版本与范围的具名裁决；分别注明G1工程、G3真实宿主、G4专业采用，不能互相代替 |
| 待复验 | 旧证据缺失、过期或受当前变化影响；历史通过事实仍保留 |
| 阻塞 | 写清原因、保留状态、解除条件和可继续的独立工作 |

技术合同、文档等非运行工作项按其具体出口说明核对结果，不伪造测试；不套用产品G1/G3/G4。工作项完成不等于整个AT通过，同一AT的E/H/B证据必须分开。

M1–M6仍可在已有授权及包出口满足时连续推进，不要求每个小项重新向Owner审批，也不把每包自测通过都写成独立验收。需要G1/G2保护的真实运行不能提前。

### 6.4 小步检查点

每个可验证工作项结束、任务/权限/结论改变、准备切换上下文或提交前，都更新检查点。不能等对话结束才集中补记；正常开发不必每改一行记录一次。

先保存原始结果与具名版本，再更新CURRENT，不反过来预写成功。当前包记录至少包含：

| 工作项ID | 当前状态 | AR/AT与证据层 | 实现/合同身份与证据位置 | 剩余动作 |
|---|---|---|---|---|

这是维护字段，不是预填验收结果。执行者填写实际值；无证据写未验证。测试记录在实际StageRoot，绑定输入、测试命令/退出码、受测代码/资源hash或具名快照及审核范围，不能只写测试数量。

StageRoot的`阶段交接.md`负责索引不可混用的证据，CURRENT负责当前判定；两者用相同检查点编号关联。新检查点保留前次证据和状态改变原因，不另建逐对话进度报告。仅文档工作且无产品StageRoot时，以具名Git差异及文档复核说明登记，不为流程制造空运行目录。

### 6.5 变更与验收失效

- 修改实现前明确工作项ID、AR需求、AT验收及本包出口。无法对应的改动不进入本版，不能以局部优化代替最终交付。
- 相关实现、共享接口、规则、输入/配置、方法或政策变化时，列出受影响消费者与验收，保留旧结果并将当前受影响项标为待复验；修复后用新证据恢复状态。无法判断影响时先核实，不默认为无影响。
- 单纯提交Git、修改无关文案或归档，不自动使全部验收失效。共享Store/Journal等变化按实际依赖扩大回归，不重审未受影响历史。
- 需求/方法/权限/验收变更先在Spec登记影响和Owner决定，再同步对应工作项；工程细化只改本包合同。不能为了把状态变绿删需求、缩验收或重新命名失败项。

### 6.6 交接与完成检查

主执行者在换对话、送审、声明阶段完成及获准提交前，逐项核对：实际改动在本包范围；计划/接口与实现一致；CURRENT没有超出证据的结论；未完成和失效项仍可见；下一动作满足依赖和权限。

阶段收尾必须回看整个交付链，明确本轮推进了哪些AR/AT、距离G1/G3/G4还缺什么；不能只报告局部测试全绿。独立审核者除检查代码外，还检查这些对应关系，不替实现者补签缺失结果。

发现不一致不得宣布该项完成，先修复或降为未验证/待复验，保留差异说明；不阻断无关且已获准的工作。最终回复简述实际成果、验证边界、剩余问题和下一动作，必须与CURRENT一致。保存检查点不等于取得Git提交或真实调用许可。

# Agent 原生 KTH 评估器交付规格

规格ID：`AG1-SPEC`  
版本：`1.1-candidate`，2026-09-18  
状态：产品方向已由Owner明确；本版详细范围与验收合同待Owner审核采用。  
实际进度与执行权限只记录于[CURRENT](D:/UGit/kth-irl-hybrid/docs/CURRENT.md)，本文不维护“最新进度”。

## 1. 不变的交付目标

**首版只交付在当前Codex宿主中加载和执行的插件，内嵌标准Skill作为工作流核心。用户在Codex中提交材料、确认评估范围，得到可追溯的评估候选报告，并可继续补证、复核和恢复。**

不要求同时交付独立Skill包或适配其他Agent；保留标准Skill结构和清晰领域边界即可，不为未来兼容提前增加多宿主框架。

不是Windows应用，不是要求用户操作的CLI，不是只有提示词的报告生成器，也不是只有底层组件的工程演示。操作系统只是宿主运行环境；辅助代码由Agent调用。

本项目采用**工程候选交付 → 与同事/业务方进行专业效果验收 → 在同一仓库分支改进**的顺序。开发人员不承担专业答案编制或投资判断责任。未确定专家不阻断规格、实现、离线工程测试；不因此伪称专业质量已经通过。

最终候选产品必须贯通：

```text
Agent接收显式附件与行动问题
→ 材料覆盖与主体/产品单元候选
→ 用户集中确认范围、时点和权限
→ 主动研究、主张与用途资格
→ 单元级五维＋融资责任主体级FRL
→ 独立正反评审、争点处理及规则求值
→ 组织政策下的D1行动判断候选
→ D2同源投影、详细报告与简明摘要
→ 在Agent中交付、追问、补证与恢复
```

“全链贯通”不意味着所有Case都必须有等级或YES/NO。缺料可形成有据的不足；执行、方法、权限或过程缺失不得伪装为企业业务NO。

## 3. 产品范围

### 3.1 首个交付范围

- 标准`SKILL.md`入口，按需加载的方法/运行参考，配套确定性工具；插件只提供发现、入口与资源定位。
- 当前Codex是首版唯一实现与验收宿主，沿用现有插件结构内嵌标准Skill；领域状态持久化，不只存在于当前对话。其他Agent适配及跨操作系统验收不在本版范围。
- 附件入口首批覆盖PDF、DOCX、ZIP及纯文本。枚举全部成员/页/段/表格覆盖，扫描或不支持内容明确列出，不以空文本判不存在。
- 从材料发现并确认多个评估单元；单元数量由材料与范围决定，不硬编码微玖三单元/五单元或某个公司。
- CRL、TRL、BRL、IPRL、TMRL按评估单元处理；FRL按融资责任主体共享，保留各单元资金需求与分配影响。
- 主动公开研究、身份/重大声明线索与必要专利资料定位；未授权访问、受限来源、无法核实均保留终态。不得声称法律/FTO意见已经成立。
- 单元级正反评审、明确反证/不足/失败、规则求值、行动判断候选、同源报告及变更比较。
- 新会话恢复、受控补证、原件保护、实际调用记录、费用或用量可见性、协作交接。

### 3.2 首版方法边界

沿用当前已批准方法及已审规则，不因工程目标变大自行扩算法：

| 维度 | 当前目录覆盖 |
|---|---|
| CRL | 13条，1–4级 |
| BRL | 36条，1–9级 |
| TRL | 25条，1–9级 |
| IPRL | 32条，1–9级 |
| TMRL | 38条，1–9级 |
| FRL | 36条，1–9级，保留限定N/A规则 |

合计180条是批准实现范围，不是完整官方方法全集。“六维候选”必须逐维声明范围；CRL达到支持上限时不能显示为已证明无法达到5级，也不能宣称完整官方CRL评价。全量CRL或其他新方法属于另行方法变更，不由本工程计划批准。

旧wheel只提供行为对照和具名来源，不是专业正确性证明。发现准则语义不可机械对应时，记录方法分歧并停止受影响求值；其他独立工程工作可继续，不自行放宽validator。

### 3.3 不在首版范围

独立Skill发行包、其他Agent适配、跨操作系统兼容矩阵、独立Web/桌面应用、多租户平台、交易执行、投资/签约/付款授权、官方KTH认证、承诺专家级正确率、全格式OCR、自动修正方法、自动联系企业或同事、远端配置和对外发布。

不创建第二套CaseStore、Provider网关或事实源，不把旧controller整体迁入，不恢复旧session/Gate体系。宿主包装不复制业务算法。

## 5. 架构与信任边界

### 5.1 四层职责

```text
标准Skill：目标、工作流、方法阅读路由、用户交互与停止边界
  ↓
宿主适配：实际工具能力、任务派发、独立上下文、执行记录
  ↓
产品服务：材料/单元/研究/评审/决策/报告编排
  ↓
既有确定性内核：Store、Journal、来源/用途、规则、trace、恢复
```

Agent负责语义候选、研究、正反推理及向用户表达；程序负责身份、资格/用途合同、规则求值、引用闭合、状态与投影。模型不能直接写最终Evidence资格、原生等级或通过标记。

CLI可以保留为内部工具与调试接口，但不是用户产品入口。不能把“用户先运行脚本造好job”算作Agent完成整链。

### 5.2 单一Codex插件交付

维护的实现只有`plugin/src/kth_hybrid/`一份。打包时装配已登记的源码、catalog和Skill资源，生成一个完整Codex插件包：

```text
插件包
  .codex-plugin/plugin.json
  skills/kth-irl-evaluator/
    SKILL.md
    references/
  scripts/kth-local.py            Agent调用的内部工具入口
  src/kth_hybrid/                 唯一运行代码，含catalog
  commands/                     仅委托Skill
```

插件包有一份源码/资源manifest，不允许人工修改打包副本。资源通过Codex提供的插件根或相对包位置解析，不硬编码开发机路径、不导入全局另一版本。本文工作仓导航链接不进入产品运行配置。标准Skill不因此变成独立发行包，首版不增加第二套装配和验收。

运行环境前提是宿主可调用Python≥3.12及声明的解析依赖；预检只检查，不自动联网安装。依赖缺失应给可读阻断，但该宿主此时不能算安装/运行验收通过。依赖如何随内部包提供、许可和身份由M6核对现有本地资源后登记，不复制整套开发环境或凭据。

### 5.3 宿主能力与来源

Codex适配必须检测文件读取、辅助代码执行、独立上下文、获准研究工具和可保存的执行记录。记录实际Codex版本/会话能力；没有的能力明确阻断相关阶段，不因选择Codex就假定全部工具存在。不要求为其他宿主设计适配层。

实际宿主Agent返回、独立Provider API返回、人工意见、测试替身使用不同来源标签。禁止把宿主模型返回伪装成`authorized_human`或把导入JSON伪装成真实Provider。

宿主任务至少绑定：Case/run、任务与角色、精确输入摘要、允许材料/用途、合同版本、实际宿主/上下文标识、开始与结束、输出摘要和执行状态。适配者核对任务闭包，并保存可取得的工具执行证据。

这些记录证明本地观测到的执行，不宣称外部公证。不允许仅凭调用者自报`verified=true`成立独立性；宿主无法证明独立上下文时记`independence_unverified`，不得交付成已完成正反独立评审。

默认使用宿主已有Agent能力；不能因为加载Skill就自动启动另一套付费API。确需外部模型或研究服务，走明确授权和统一执行边界。宿主未提供精确token/费用时显示未知；不得凭空填零，额外API预算不得借宿主路径绕过。

### 5.4 范围、材料与研究

先登记全部显式材料和提取覆盖，再提出单元与相关主张。不得默认只看BP页17，或由开发者先选好证据后称自动发现。

用户一次集中确认主体、单元、行动、时点和权限，不承担逐准则判定。保存模型原候选与人确认的差异，避免隐藏人工贡献。

来源资格观察不因新用途政策被抹去。访谈、自述、测试记录分别有可证明/不可证明边界；同字节不同导入实例保留身份。来源与时点未知不能通过自动登记当前日期变成历史事实。

公开研究问题由系统形成并执行获准访问，区分`answered / contradicted / unresolved_after_search / blocked_by_access / not_applicable`。搜索摘要不是原始证据，检索无结果不证明不存在，访问失败不是项目方业务缺陷。

### 5.5 专业评审与规则

专业执行状态与结果分别记录：

- `pending/running/blocked/failed`没有业务复核结论；
- 成功执行可给`supports/refutes/insufficient`，支持与反证可以构成争议；
- 漏合同字段、非法引用、越权推断属于执行/合同失败，不能静默记业务不足；
- 材料本身缺少字段时明确未知和缺项，允许合法不足。

专业判断不能靠字段名暗示通过。每个实质finding应带原文定位、适用单元、解释、限定条件及反证。复用既有六维内核时通过显式版本适配，不直接改旧结果或降低旧接口约束。

六维各自遵守维度含义、证据类型、累计规则及N/A，不以一个通用评分器替代。对抗输出应处理真实争点，轮数/文本量不是质量证明。专业效果验收在工程候选交付后，由同事或业务审阅者承担。

### 5.6 D1、D2与候选权限

首发行动固定为`external_investment.approve_diligence_or_validation`：只讨论有上限的尽调/验证。运行前由用户确认具体行动、时间/资源上限、责任和禁止事项，不能由模型自行猜。

组织政策必须版本化并有采用依据。程序可以从已批准的政策谓词和受控候选推导D1候选，但不得发明投资门槛或隐藏加权。旧政策若只有有限逻辑，报告如实披露，不冒称完整组织制度。

本版交付的是**内部评估候选**：即使候选值为YES，也不表示组织已实际批准行动，更不授权投资、付款或签约；正式采用仍由有权人员决定。没有可用政策时输出`DECISION_UNAVAILABLE`及精确原因，不能为打通演示填YES/NO。

D2是信息投影，不是第二次投资决策。详细报告、简明摘要和审计视图共享事实版本；自由写作只能组织表达，不能修改上游结论、关键反方或权限。报告改写不触发新评估；新事实/方法/政策需新身份和影响分析。

## 6. 完成标准分层

| 门 | 必须取得的证据 | 不需要什么 |
|---|---|---|
| G0 规格采用 | Owner接受本版范围、顺序与验收边界；CURRENT登记采用版本和实施权限 | 不要求开发者成为专业专家 |
| G1 离线工程候选 | 实际同产品路径正常/不足/反证/失败测试、恢复、包验证；独立工程审核 | 不要求预先确定真实企业黄金等级 |
| G2 真实运行许可 | 新材料/用途/宿主或API/研究范围、窗口、预算与停止策略；必要安全项已审 | 不继承旧9月16日调用窗口 |
| G3 工程交付 | 当前Codex的全新真实会话端到端、恢复、可追溯报告和协作包；见AT-15/16 | 不要求其他Agent/独立Skill包验收，也不等于完整专业质量通过 |
| G4 专业复核与采用 | 同事/业务方对精确版本、输入和结果给具名反馈；只有明确认可适用范围才记专业采用 | 不由开发者或另一模型代签 |

工程交付状态为`engineering_delivered / professional_review_pending`，这是可交同事使用和评价的候选版本，不是生产专业认证。

专业状态依次独立记录`pending / feedback_received / changes_requested / accepted_scope`。收到“不认可、需要修改”的意见只证明复核发生，不是通过；只有实际专业负责人明确接受具体版本、结果与适用范围，才可进入`accepted_scope`。改动受影响后该范围需复验，不继承旧采用效力。

仅有Skill文件、CLI通过、模拟流程、安装成功，或所有资格全部阻断导致专业链未执行，均不得宣称G3完成。真实结果全部不足时，必须证明实际研究/专业链已执行、缺口有依据，且只声明工程链成功；正向专业质量仍未验证。

工程可继续不意味着权限可跳过：当前没有真实调用批准；当前消息也不批准安装依赖、远端动作、提交或推送。

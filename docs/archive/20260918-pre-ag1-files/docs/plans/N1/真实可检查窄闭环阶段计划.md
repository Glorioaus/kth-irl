# KTH 真实可检查窄闭环阶段计划

版本：N1-plan-v4，2026-09-17，自包含工作仓版。路线及依赖收口已由Owner采用；**N1业务阶段仍待审核采用，本次依赖改动不等于启动N1。**

**目标：**在现有仓库中实现并接通真实材料到专业复核、诚实结果及人工检查的窄闭环，而不是交付孤立模块。

**架构：**保留原件、Journal、追溯、规则内核和受控队列；分离资格观察与用途裁定，明确专业结果合同，并接入现有应用路径。预算、授权和真实调用经过统一执行边界。新增窄范围编排复用这些组件，不建另一套CaseStore、Provider、方法引擎或报告事实源。

**技术边界：**沿用本地Python≥3.12、SQLite、文件原件仓、pytest和Markdown；不装新依赖、不新建仓库/worktree。本阶段不要求新UI或完整Plugin安装。

**唯一状态入口：**[CURRENT](../../CURRENT.md)。完整执行输入见[新执行对话完整输入](新执行对话完整输入.md)。本文与执行输入采用同一N1-plan-v4合同；旧仓外v2仅是历史。v4只将已核验的资源和Case来源切到仓内，不改变N1业务范围。

## 1. 收口决定

旧W1–W4合并为阶段N1：

```text
P1 合同与信任输入
  → P2 模块替换、实际应用接线及预算闭合
  → P3 离线端到端、恢复与可读结果
  → G1 调用前独立工程审核
  → G2 Owner新的真实调用授权＋人工参考标准就绪
  → P4 真实候选与专业复核
  → G3 人工质量签审＋独立阶段核对
  → 阶段结束
```

Owner一次批准离线工作范围后，P1–P3连续自主推进，包间只记录工程检查点，不逐函数、逐文件、逐测试或逐Claim请示。合同细化不得改变本计划的业务边界；需要改变判据、来源资格含义、时点问题或投入范围时才集中升级。

G1/G2/G3是必要的信任与授权门，不是消除自主执行的理由。实现者不能兼任自身的独立审核，也不能用“可以继续自主执行”绕过新的外部调用批准。独立审核者暂不可用时，停为待审，不自签。

“生产接线”指**接入将来真正使用的同一CLI/应用服务/队列/runner路径**，先在新受控Case副本中离线运行；不代表改写旧生产Case、立即外发或发布。

## 2. 固定范围与材料

一个内部审阅Case、一个明确候选评估单元、最多3个活跃主张、仅两个准则：**TRL5-C1、TRL6-C2**。冻结范围在候选输出之前，不让模型或执行者看到结果后换准则。旧TRL3-C2只作离线语义反例，不纳入本次真实任务分母。

真实运行不能仅复用旧模型结果来冒称自动化成功：应有当前冻结请求产生的新候选与真实专业复核。旧响应仅为带历史身份的参考/离线重放材料，不改request/job/CaseBasis标识。新候选如全部不能依法消费，应如实停止为材料/资格阻断，**不算阶段闭环完成**。

本阶段不计算完整TRL累计等级、不生成六维完成标签、不做D1/D2、投研报告、CEO Brief、投资决定或发布。交付的中文审阅记录是窄范围结果，不是正式评估报告。原完整产品目标不撤销。

## 4. 共同合同：所有消费者只用一套

P1把以下契约写入仓内一份`docs\specs\narrow-loop-v1.md`。它是工程合同，不是新的KTH方法批准；执行者在P1一次冻结字段、函数签名与输入输出例子后直接进入P2，不等待逐字段确认。

### C1 范围与身份

`NarrowRunSpec`含材料集合、精确投影、CaseBasis、评估单元、两个准则ID、最多3Claim、catalog与资格/用途/专业合同版本。scope/材料/时点/方法变化必须新建运行身份。范围外条目记`not_in_scope`，不隐去、也不创建新任务。

模型请求的准则清单和返回验证器同时检查两个准则，不仅在prompt写“最多2个”。旧全部六维profile保持原合同；新增明确窄profile/模式，不能把六维manifest改成接受缺维。

### C2 资格观察与用途

来源/主体/时间/独立性观察及其原理由保留。受控读取层重建证明，纯裁定函数不把调用者字典或自报`verified=true`当事实。

`company_self_statement`可在已核来源、主体、时间及同件重复导入关系下使用，不因重复实例独立性UNKNOWN一概阻断；原UNKNOWN和“未独立核实”限制仍保留。未知原因不是重复时不得同样放行。相同hash只证明相同内容，不证明现实出处；不同hash也不自动独立；不得删除source或硬编码计数。

用途许可绑定Claim、criterion、scope、CaseBasis、资格视图、关系证明、政策版本和摘要；ProposalQueue、ReviewQueue、runner与trace同一验证规则。旧v4不能因新增版本重新变绿。

### C3 专业结果与失败

执行状态`pending/running/succeeded/blocked/failed`与专业结果分开。只有`succeeded`才可产生`supports/refutes/insufficient`；失败或未执行时结果为null。支持与反证可同时登记为争议，不强迫消除。

每个实质finding包含原文定位、原文/解释区别、适用配置/系统边界、证明/不证明范围及引用。关键字段在材料中没有时写“未知＋具体缺项”，不得补值。

两准则适配现有TRL规则：TRL5-C1需要`integrated_relevant_environment_test`，TRL6-C2需要`prototype_near_operational_spec`；共同核对`project_specific/configuration_id/system_boundary/test_environment/test_method/measured_results/requirements_thresholds/environment_kind`以及适用的component/system条件。字段语义以当前kernel和canonical条目核对，不创造新阈值。

区分“响应缺少合同要求的字段”与“材料明确无法提供该字段”：前者是合同执行失败；后者是有理由的insufficient。`supports`缺失必需证明不得默默降为公司技术不达标，须拒绝该支持结论并记录原因。

只有有原文反证的`refutes`才可适配现有`does_not_support`；普通缺料不映射`does_not_support/not_met`。`insufficient`保留缺口及专业复核身份，以规则既有不足路径处理；`failed`不进入业务求值。不修改kernel来迎合模型输出。

### C4 人可读输出

单一事实结果对象产生`窄闭环审阅记录.md`及对应`result.json`，包含输入范围、逐Claim来源/资格用途、候选解释、专业复核、支持/反证/缺料、失败、可追溯引用与限制。历史模型、当前真实模型、人工和合成来源分列。

用户只需打开中文记录即可核查，不需编辑JSON/hash。机器文件保留可重建身份。不得输出“完整TRL评级”“六维通过”或正式D1；renderer不能增加事实。

### C5 调用与预算

统一预算账本拥有全部关联scope的事务内汇总与预留，预算读取不能由调用方传入过时余额。迁移/授权修订/关联scope均按最终dispatch→store路径验证，不能只测试辅助函数。关联未知则拒绝。

跨Case只有显式、可验证的预算继承或集中单一账本，不凭相同scope字符串宣称共享；本阶段限制一个活跃派发者，并验证重复进程被拒。业务预算不是每个新Case自动重置。

请求级输入上界绑定最终消息字节摘要、精确模型/分词方法或可论证上界、包装开销和版本；非空`evidence_source`不构成证明。缺计数能力或费用依据时形成阻断，不安装依赖或调用在线计数来绕开禁网。

历史3次请求的2项未知量必须逐mission对账或有证据的保守占用，不补造丢失响应。真实调用授权明确历史如何计入；即使Owner批准新预算，也须显式区分，而非隐藏旧消耗。

### 早期就已明确的产品目标

- 用户提交明确附件并确认一个行动，而不是让用户先按六维整理数据。
- Evidence与提取文本、推断、Finding、Assessment和Decision分开；原件hash不证明事实真实。
- 六维独立，不允许总分或隐藏聚合；D1仅决定有限尽调/验证，不批准投资、签约或付款。
- 公开研究由系统承担，私有残余事实才向项目方请求；搜索摘要不替代原始证据。
- 正反初评独立、最强反方和少数意见保留；有界不等于任意削减专业深度。
- CEO、分析员、审计视图来自同一事实，不通过改报告措辞改变业务判断。
- 已完成部分保留，失败停在精确位置；流程失败不是企业业务NO。
- 宿主、模型、Skill和具体技术可替换，领域语义不随宿主变化。

### 路线图直接纠正了“以模块数量作为进展”的倾向

路线图开头明确：**用户里程碑看用户此时能完成什么判断，schema、validator、Agent、Skill、Receipt及单维纵切属于内部使能，不应冒充产品里程碑。**

其主路径为发起评估案→事实基础→六维状态→行动决定→同源视图/补证→有真实需要才扩展宿主。文档还明确写道：**Monako直接评审是产品发现和回归样本，不是这些能力已经产品化的证明。**

这不是要恢复早期所有治理字段和审批流程，而是说明当前“真实可检查窄闭环”的阶段目标有早期需求依据；不能把孤立模块、历史报告或测试数量作为完成。

6月2日运营效率路线图和7月15日世界模型规划也已补下载并核读定位：它们属于更上层的组织信息→决策→行动背景，KTH是投资评估子系统之一；不把它们整套扩入当前N1。

## 4. 怎样用这些资料，不再丢成功也不继承错误

按四种用途使用：

1. **需求来源：**7月17日PRD/路线图，回答最初要给用户什么，不让庞大实现倒推产品目标。
2. **真实输入样本：**Monako材料池、微玖BP+四访谈，保留来源/时点/重复关系；不是预先合格Evidence。
3. **候选效果对照：**同事报告，学习产品单元、反证、限制和报告结构；不复制等级或最终YES/NO。
4. **回归负例/运行证据：**机器人错误稿、平台微玖高分混合稿、用户被质疑稿、两次失败receipt及macOS成功结构。

后续合同应显式检查：输入集合是否相同；是否混入重写稿/额外搜索；评估单元、时间、模型/方法/政策是否一致；报告是否使用同一事实来源。只有这些可核，才讨论结果差异属于bug、方法差异或材料差异。

这次补充不执行新业务分析，不改变当前N1授权，不自动外发新增访谈，不重审全部旧代码。完成资料纠错后回到当前闭环任务。
